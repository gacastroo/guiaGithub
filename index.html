GIT VS GITHUB: La analogía más fácil

"Git es el cerebro 🧠, GitHub es la red social 🌐."

"Git guarda tu código, GitHub lo presume."

Git es una herramienta de control de versiones que permite guardar el historial de cambios de un proyecto. Gracias a Git puedes saber qué se ha modificado, cuándo se hizo, quién lo hizo y volver a una versión anterior si algo sale mal.

GitHub es una plataforma online donde puedes subir tus repositorios Git, compartir código, colaborar con otras personas y mostrar tus proyectos de forma profesional.

Usar Git y GitHub es importante porque te ayuda a trabajar de forma más ordenada, evitar perder cambios, colaborar en equipo y construir un portfolio visible para empresas y reclutadores.

Git

  • Software local (en tu ordenador)
  • Control de versiones
  • Guarda instantáneas del proyecto
  • Ideal para uso individual
  • Funciona sin internet

GitHub

  • Plataforma web
  • Colaboración en equipo
  • Basado en Git
  • Gestión de proyectos
  • Red social para código

¿Qué es el control de versiones?

Un sistema que permite gestionar y rastrear los cambios en el código fuente a lo largo del tiempo, facilitando la colaboración y el desarrollo eficiente de software.

Estos son los cambios que necesitas hacer para iniciar un proyecto con Git:

git init
Crea un repositorio nuevo en la carpeta actual

Crea una nueva conexión a un repositorio remoto.
git clone <url>
Descarga un repositorio existente

Descarga los cambios del repositorio remoto

Son los comandos que usas diariamente:

git status
Muestra qué ha cambiado
git add .
Prepara todos los cambios para el commit

Guarda los cambios en el historial
git push origin main
Sube los cambios a GitHub
git pull origin main
Baja los cambios del remoto

4 · Ramas

Estos son los comandos que usas para trabajar con ramas:

git switch -c mi-rama
Crea y cambia a una rama nueva
git switch main
Vuelve a la rama principal
git merge mi-rama
Une la rama con la actual

⚠️ Un merge puede causar conflictos si los cambios en ambas ramas son incompatibles. Cuando haces un merge, no hay forma de deshacerlo una vez que se resuelven los conflictos.

5 · Si algo va mal

git log --oneline
Ver historial de commits resumido
git restore <archivo>
Descartar cambios en un archivo
git restore --staged <archivo>
Quitar un archivo del staging

Git guarda tu trabajo en dos pasos: preparar y guardar. Cuando cambias archivos, Git ve esos cambios, pero no los guarda directamente. Primero eliges qué cambios quieres incluir (eso es staging o preparar). Luego los guardas con un commit. Es como hacer una foto: primero eliges qué quieres que salga en la foto (preparar) y luego haces la foto (guardar).

Errores comunes en Git/GitHub y cómo solucionarlos

Esta sección está pensada como un botiquín de primeros auxilios: buscas el mensaje de error, entiendes por qué aparece y aplicas la solución segura antes de tocar comandos peligrosos.

🧭

Regla de oro antes de arreglar nada

  • Mira el estado del repositorio con git status.
  • Lee el mensaje completo del error: normalmente Git ya te dice qué falta.
  • No uses --force, reset --hard o clean -fd si no sabes exactamente qué borran.

Diagnóstico rápido

Cuando Git se queja, estos comandos te dicen casi siempre dónde está el problema:

git status
Muestra cambios pendientes, conflictos, rama actual y si hay commits por subir.
git branch
Lista tus ramas locales y marca con un asterisco la rama en la que estás.
git remote -v
Comprueba a qué repositorio de GitHub está conectada tu carpeta local.
git log --oneline --decorate -5
Muestra los últimos commits de forma resumida para saber dónde estás.

Errores frecuentes

Carpeta incorrecta

fatal: not a git repository

Aparece cuando ejecutas comandos de Git fuera de una carpeta que tenga repositorio. Normalmente estás en otra ruta o todavía no has hecho git init/git clone.

Solución

  1. Entra en la carpeta correcta del proyecto.
  2. Si el proyecto aún no usa Git, inicialízalo. 
cd ruta/de/tu/proyecto
git status
# si no era un repositorio todavía:
git init
Identidad Git

Please tell me who you are

Git no sabe con qué nombre y correo debe firmar tus commits. No es un fallo de GitHub: es configuración local de Git.

Solución

git config --global user.name "Tu Nombre"
git config --global user.email "tu@email.com"

Después vuelve a ejecutar el commit.

Sin cambios

nothing to commit, working tree clean

Significa que Git no ve cambios pendientes. Puede ser correcto, o puede que hayas olvidado guardar el archivo, estés en otra carpeta o el archivo esté ignorado por .gitignore.

Solución

git status
git status --ignored

Si el archivo sale como ignorado, revisa tu .gitignore.

Remote duplicado

remote origin already exists

Tu proyecto ya tiene un remoto llamado origin. Suele pasar cuando intentas conectar otra vez la misma carpeta con GitHub.

Solución

git remote -v
# cambiar la URL del remoto existente:
git remote set-url origin https://github.com/usuario/repositorio.git
Rama sin commits

src refspec main does not match any

Git no encuentra la rama que quieres subir. Lo más común es que todavía no tengas ningún commit o que tu rama se llame master en vez de main.

Solución

git status
git add .
git commit -m "chore: primer commit"
git branch -M main
git push -u origin main
Push rechazado

failed to push some refs / non-fast-forward

GitHub tiene commits que tú no tienes en local. Git evita que sobrescribas trabajo remoto sin revisarlo antes.

Solución segura 

git pull origin main
# si aparecen conflictos, resuélvelos
git status
git push origin main

Si estás trabajando en equipo, evita git push --force salvo que sepas exactamente lo que haces.

Rama protegida

Cannot update this protected ref / protected branch hook declined

La rama está protegida en GitHub. Es habitual en main o master: no puedes subir cambios directamente y debes usar una rama + Pull Request.

Solución

git switch -c feature/mi-cambio
git add .
git commit -m "feat: describir cambio"
git push -u origin feature/mi-cambio

Después abre un Pull Request en GitHub hacia main.

Autenticación

Authentication failed / password authentication removed

GitHub no acepta la contraseña normal de tu cuenta para operar por HTTPS. Debes iniciar sesión con el gestor de credenciales, usar un token personal o configurar SSH.

Solución recomendada

  1. Cierra sesión o borra credenciales antiguas en el gestor de credenciales de Windows/macOS.
  2. Vuelve a hacer git push y autentícate en la ventana del navegador. 
git remote -v
git push origin main
Permisos

Repository not found / Permission denied (publickey)

Puede significar que la URL del remoto está mal, que no tienes permisos en ese repositorio o que tu clave SSH no está añadida a GitHub.

Solución

git remote -v
# HTTPS:
git remote set-url origin https://github.com/usuario/repositorio.git
# SSH, si tienes clave configurada:
git remote set-url origin git@github.com:usuario/repositorio.git

Si el repositorio es privado, confirma que tu usuario tiene acceso.

Cambios locales

Your local changes would be overwritten by merge

Tienes cambios sin guardar en commit y Git no quiere pisarlos al hacer pull, merge o cambiar de rama.

Soluciones posibles 

# opción A: guardar los cambios en un commit
git add .
git commit -m "wip: guardar cambios antes de actualizar"

# opción B: guardarlos temporalmente
git stash
git pull origin main
git stash pop
Conflicto

CONFLICT (content): Merge conflict

Dos ramas han cambiado la misma zona de un archivo. Git no puede decidir solo y necesita que elijas la versión correcta.

Solución

git status
# abre los archivos en conflicto, elimina <<<<<<< ======= >>>>>>>
git add archivo-resuelto
git commit -m "fix: resolver conflicto"

Si todavía no quieres resolverlo, puedes cancelar el merge con git merge --abort.

.gitignore

.gitignore no me funciona

Si un archivo ya fue añadido al repositorio, .gitignore no lo elimina automáticamente del seguimiento. Solo evita que se añadan archivos nuevos que coincidan con sus reglas.

Solución

git rm --cached archivo.txt
# o para una carpeta:
git rm -r --cached carpeta/
git add .gitignore
git commit -m "chore: actualizar gitignore"
Saltos de línea

LF will be replaced by CRLF

Es un aviso habitual en Windows. Git te está diciendo que convertirá saltos de línea entre formatos Windows y Linux/macOS. No suele ser grave, pero puede molestar en proyectos compartidos.

Solución habitual 

# en Windows suele usarse:
git config --global core.autocrlf true

# en Linux/macOS suele usarse:
git config --global core.autocrlf input

Comandos peligrosos: úsalos con cuidado

⚠️ Puede borrar trabajo local

  • git reset --hard
  • git clean -fd
  • git checkout -- archivo

⚠️ Puede afectar al equipo

  • git push --force
  • git branch -D nombre-rama
  • git push origin --delete nombre-rama

Antes de usar uno de estos comandos, haz una copia, pregunta al equipo o guarda tus cambios en una rama temporal. 

git switch -c backup/antes-de-arreglar
git add .
git commit -m "backup: guardar estado antes de corregir"

Miniguía: ¿Dónde vive tu código?

Para trabajar con GitHub, imagina que tienes dos "copias" de tu proyecto:

  • Repositorio Local: Es la carpeta en tu ordenador. Es donde editas tus archivos día a día. GitHub no ve esto hasta que tú lo envías.
  • Repositorio Remoto: Es la copia en los servidores de GitHub. Es tu respaldo en la nube y el lugar donde los demás ven tu código.

¿Cómo se conectan?

Tú trabajas en tu Local. Cuando quieres que GitHub se entere, haces un commit (guardar foto instantánea) y luego un push (enviar a la nube).

2. Vincular tu repositorio con GitHub

Antes de empezar a trabajar, necesitas conectar tu proyecto local con el repositorio remoto de GitHub. Hay dos formas principales de hacerlo:

Opción A · Clonar un repositorio

Usa esta opción si el repositorio ya existe en GitHub y quieres descargarlo a tu computadora.

Opción B · Vincular una carpeta local

Usa esta opción si ya tienes una carpeta con archivos en tu computadora y quieres subirla a GitHub.

Opción A: Clonar un repositorio existente

  1. Entra al repositorio en GitHub.
  2. Haz clic en el botón verde Code y copia la URL del repositorio.
  3. Abre la terminal en VS Code con Ctrl + Ñ o desde Terminal → New Terminal.
  4. Ve a la carpeta donde quieres guardar el proyecto, por ejemplo:
cd Desktop

Después, ejecuta el comando git clone:

git clone https://github.com/usuario/nombre-repositorio.git

Entra dentro de la carpeta que se acaba de descargar:

cd nombre-repositorio

Al clonar un repositorio, Git crea automáticamente la conexión con GitHub. Esa conexión se llama normalmente origin.

Puedes comprobarlo con:

git remote -v

Si todo está correcto, verás algo parecido a esto:

origin  https://github.com/usuario/nombre-repositorio.git (fetch)
            origin  https://github.com/usuario/nombre-repositorio.git (push)

Opción B: Vincular una carpeta local con GitHub

Usa esta opción si ya tienes tu proyecto creado en tu computadora y quieres conectarlo con un repositorio nuevo de GitHub.

  1. Crea un repositorio nuevo en GitHub.
  2. Copia la URL del repositorio. Será parecida a esta:
https://github.com/usuario/nombre-repositorio.git

Abre tu proyecto en VS Code y asegúrate de estar dentro de la carpeta correcta en la terminal.

Puedes comprobarlo con:

pwd

Ahora ejecuta estos comandos en orden:

git init
            git add .
            git commit -m "feat: initial commit"
            git branch -M main
            git remote add origin https://github.com/usuario/nombre-repositorio.git
            git push -u origin main

¿Qué hace cada comando?

  • git init: convierte tu carpeta en un repositorio local.
  • git add .: prepara todos los archivos para guardarlos.
  • git commit -m "feat: initial commit": crea el primer punto de guardado.
  • git branch -M main: asegura que la rama principal se llame main.
  • git remote add origin: conecta tu repositorio local con el repositorio remoto de GitHub.
  • git push -u origin main: sube tu proyecto a GitHub y deja la rama conectada para futuros pushes.

Resumen fácil: git clone descarga un proyecto que ya existe en GitHub. git remote add origin conecta una carpeta local con un repositorio remoto.

Después de hacer esto una vez, tu flujo diario será:

git add .
          git commit -m "tipo: mensaje claro"
          git push

Nota: sustituye usuario y nombre-repositorio por los datos reales de tu cuenta y de tu repositorio.

5. Como hacer un commit profesional

Un commit profesional es claro, conciso y descriptivo. Sigue esta estructura:

Estructura de un commit

git commit -m "tipo: descripción breve"

Tipos

feat Nueva funcionalidad
fix Corrección de bugs
perf Mejora de rendimiento
refactor Cambio interno sin afectar comportamiento
style Formato (espacios, tabs, etc.)
docs Documentación
test Tests
build Build, dependencias, scripts
ci Integración continua

Reglas

  • Imperativo → "add", "fix", "update"
  • Máximo ~50 caracteres
  • Sin punto final
  • 1 commit = 1 cambio
  • Mensaje claro: qué y por qué

Nota: Cuanto más claro sea el mensaje, mejor será para otros desarrolladores. Asegurate de dejar claro que archivo estás modificando.

¿Qué es una rama (branch)?

"Una rama es como una copia paralela de tu proyecto donde puedes experimentar sin miedo a romper nada."

"La rama main es el tronco del árbol. El resto son ramas que crecen a los lados."

Cuando creas una nueva rama, Git hace una copia del estado actual de tu código. Puedes modificarla libremente y, si todo va bien, unirla de nuevo a main. Si algo sale mal, simplemente la eliminas.

¿Por qué usar ramas?

❌ Sin ramas

  • Editas directamente en main
  • Un error rompe todo el proyecto
  • Difícil trabajar en equipo
  • No puedes probar cosas nuevas con seguridad

✅ Con ramas

  • Cada tarea tiene su propio espacio
  • main siempre queda estable
  • Varios desarrolladores trabajan en paralelo
  • Experimentas sin miedo

Este diagrama muestra cómo una rama se separa de main, recibe commits propios, y luego se fusiona.

Flujo de trabajo con ramas

🌿
1

Crea la rama

Parte siempre desde main actualizado

git switch -c feature/mi-nueva-funcionalidad

↓
✏️
2

Trabaja y haz commits

Edita archivos y guarda tus avances con commits descriptivos

git add . && git commit -m "feat: añadir login"

↓

Publica tu rama para que otros la vean o para hacer un Pull Request

Comandos esenciales de ramas

Crear y navegar

git switch -c nombre-rama
Crea una rama nueva y cambia a ella directamente
git switch nombre-rama
Cambia a una rama ya existente
git branch
Lista todas las ramas locales (la activa aparece con *)
git branch -a
Lista ramas locales Y remotas

Fusionar y eliminar

git merge nombre-rama
Fusiona la rama indicada en la rama actual
⚠️

Consecuencias de hacer un merge

  • Los commits de la rama fusionada quedan integrados permanentemente en la rama destino.
  • Puede generar conflictos de merge si ambas ramas modificaron las mismas líneas. Tendrás que resolverlos manualmente antes de continuar.
  • Una vez resueltos los conflictos y confirmado el merge, no se puede deshacer fácilmente (requiere git revert o git reset con cuidado).
  • En proyectos compartidos, un merge directo sin Pull Request puede saltarse la revisión del equipo.
  • Asegúrate de estar en la rama correcta antes de ejecutarlo (git branch para comprobarlo).
git branch -d nombre-rama
Elimina una rama local (solo si ya fue fusionada)
🚨

Consecuencias de eliminar una rama local

  • git branch -d solo borra la rama si ya fue fusionada, lo cual es una protección. Pero git branch -D (mayúscula) la elimina aunque tenga commits sin fusionar, perdiendo esos cambios.
  • Una vez eliminada la rama local sin haber hecho push, los commits exclusivos de esa rama se pierden.
  • Si otro compañero tenía esa rama como referencia, deberá actualizar su repositorio local.
git push origin --delete nombre-rama
Elimina la rama también del repositorio remoto
🚨

Consecuencias de eliminar una rama remota

  • La rama desaparece del repositorio remoto para todos los colaboradores del proyecto.
  • Cualquier Pull Request abierto basado en esa rama quedará automáticamente cerrado o huérfano.
  • Los compañeros que tengan la rama en local recibirán errores al hacer git fetch o git pull si intentan actualizarla.
  • La acción no tiene confirmación previa: se ejecuta de inmediato. Confirma bien el nombre antes de lanzar el comando.

Pull Request: la pieza clave en equipo

Cuando trabajas en GitHub, en lugar de hacer merge directamente, lo normal es abrir un Pull Request (PR). Es una solicitud para que tus compañeros revisen tu código antes de integrarlo en main.

  1. Sube tu rama con git push origin nombre-rama
  2. En GitHub, aparece un botón "Compare & pull request" — haz clic
  3. Escribe una descripción de qué cambios hiciste y por qué
  4. Tus compañeros revisan, comentan y aprueban (o piden cambios)
  5. Cuando todo está bien, se hace clic en "Merge pull request" ✅

Conflictos de merge: ¿qué son y cómo resolverlos?

Un conflicto ocurre cuando dos ramas modifican la misma línea de un archivo. Git no sabe cuál versión conservar y te pide que decidas tú.

Git marcará el conflicto así en el archivo:

<<<<<<< HEAD (tu rama actual)
console.log("Hola mundo");
=======
console.log("Hello world");
>>>>>>> feature/traduccion

Simplemente edita el archivo, deja solo la versión correcta, guarda y haz un commit nuevo. ¡Conflicto resuelto!

Conflictos de merge: qué son y por qué ocurren

Un conflicto ocurre cuando dos ramas han modificado la misma línea del mismo archivo de formas distintas y Git no puede decidir cuál versión conservar. No es un error: es Git pidiéndote que tomes una decisión.

"Imagina que tú y un compañero editáis el mismo párrafo de un documento compartido al mismo tiempo. Cuando intentáis unir los cambios, alguien tiene que decidir qué versión queda. Eso es exactamente un conflicto de merge."

¿Cuándo ocurre un conflicto?

✅ Sin conflicto

  • Dos ramas modifican archivos distintos
  • Dos ramas modifican líneas distintas del mismo archivo
  • Solo una rama ha modificado un archivo; la otra no lo ha tocado

⚠️ Con conflicto

  • Dos ramas modifican la misma línea del mismo archivo de forma diferente
  • Una rama elimina un archivo que la otra ha modificado
  • Ambas ramas añaden contenido en la misma posición del mismo archivo

Visualización: cómo nace un conflicto

El conflicto no aparece cuando haces los commits, sino cuando intentas fusionar las ramas.

rama main

# commit base (compartido)
function saludo() {
  return "Hola"
}
↓
# commit B — alguien en main escribe:
function saludo() {
  return "Hola mundo"
}
mismo archivo

rama feature

# commit base (compartido)
function saludo() {
  return "Hola"
}
↓
# commit D — alguien en feature escribe:
function saludo() {
  return "Hello world"
}
↓ git merge feature ↓
# Git no sabe qué línea elegir y marca el conflicto así:
function saludo() {
  <<<<<<< HEAD
    return "Hola mundo"
  =======
    return "Hello world"
  >>>>>>> feature/traduccion
}

Clave: Git no elimina tu código. Lo marca con señales para que tú decidas qué versión queda. Los marcadores <<<, === y >>> son temporales; desaparecen una vez que resuelves el conflicto.

Cómo leer los marcadores de conflicto

Cuando abres un archivo en conflicto verás tres marcadores especiales. Cada uno tiene un significado concreto:

Marcador Qué significa
<<<<<<< HEAD Inicio del bloque de tu rama actual (la rama en la que estás).
======= Separador entre las dos versiones. Lo que hay arriba es tuyo; lo que hay abajo viene de la otra rama.
>>>>>>> feature/nombre Fin del bloque de la rama que estás fusionando.

Tres escenarios reales de conflicto

Estos son los conflictos que encontrarás con más frecuencia en proyectos reales.

Escenario 1 · Texto cambiado en la misma línea

El caso más común. Dos personas editan el mensaje de un mismo botón o la misma variable de configuración. 

<<<<<<< HEAD
const TITULO = "Mi aplicación"
=======
const TITULO = "App de gestión"
>>>>>>> feature/renombrar

Solución: elige uno de los dos valores (o escribe uno nuevo), borra los tres marcadores y guarda. 

const TITULO = "App de gestión"

Escenario 2 · Función modificada de forma distinta

Una persona añade validación a una función; otra la refactoriza al mismo tiempo.

<<<<<<< HEAD
function guardar(datos) {
  if (!datos) return;
  db.insert(datos);
}
=======
function guardar(datos) {
  db.insert(datos);
  console.log("guardado");
}
>>>>>>> feature/logging

Solución: en este caso lo correcto probablemente es combinar ambos cambios manualmente: 

function guardar(datos) {
  if (!datos) return;       // validación de HEAD
  db.insert(datos);
  console.log("guardado");  // logging de feature
}

Escenario 3 · Archivo eliminado vs. modificado

Una rama elimina un archivo que la otra ha modificado. Git no sabe si debes conservarlo o borrarlo. 

CONFLICT (modify/delete): config.js deleted in feature/limpiar
and modified in HEAD. Version HEAD of config.js left in tree.

Solución: decide explícitamente si el archivo debe existir o no: 

# Opción A: conservar el archivo (quedarse con HEAD)
git add config.js

# Opción B: eliminar el archivo (aceptar el borrado de feature)
git rm config.js

Cómo prevenir conflictos (buenas prácticas)

Los conflictos no se pueden eliminar del todo, pero sí reducir con buenos hábitos de equipo:

  • Actualiza tu rama antes de empezar a trabajar. Haz git pull origin main cada mañana para partir siempre del código más reciente.
  • Ramas pequeñas y de corta duración. Cuanto más tiempo vive una rama sin fusionarse, más diverge de main y más conflictos acumula.
  • Comunica qué archivos estás tocando. En equipo, avisad cuando vais a modificar archivos de configuración compartida como .env.example, package.json o archivos de rutas.
  • Haz merge frecuente de main en tu rama. En lugar de esperar al final, trae los cambios de main a tu rama periódicamente: 
    git switch mi-rama
git merge main
  • Usa Pull Requests con revisión. El proceso de PR detecta posibles conflictos antes de fusionar y permite que alguien más revise los cambios.

"Un conflicto que se resuelve el mismo día en que aparece es un problema de 2 minutos. Un conflicto acumulado durante dos semanas puede ser un problema de dos horas."

¿Qué es un .gitignore?

Un archivo .gitignore es un fichero de configuración utilizado por Git que le indica qué archivos o carpetas debe ignorar, es decir, no incluir en el control de versiones.

Aunque esos archivos existan en tu proyecto, Git no los rastreará ni los subirá al repositorio.

¿Por qué usar .gitignore?

  • Seguridad: evita subir datos sensibles como contraseñas o claves API.
  • Rendimiento: reduce el tamaño del repositorio.
  • Orden: evita incluir archivos innecesarios o generados automáticamente.
  • Colaboración: mantiene el proyecto limpio y consistente entre equipos.

¿Cómo funciona?

El archivo .gitignore contiene patrones que indican qué ignorar: 

node_modules/
*.log
.env
dist/
Patrón Significado
node_modules/ Ignora toda la carpeta de dependencias
*.log Ignora cualquier archivo con extensión .log
.env Ignora el archivo de variables de entorno sensibles
dist/ Ignora la carpeta de archivos generados en el build

Bonus: Integración con VS Code

Visual Studio Code es un editor de código muy popular que tiene integración nativa con Git. Esto significa que puedes hacer commits, ver cambios, manejar ramas y resolver conflictos sin salir del editor.

Nota: Para usar Git en VS Code, asegúrate de tener Git instalado en tu sistema y que VS Code lo reconozca. Puedes comprobarlo abriendo la terminal integrada y ejecutando git --version.

1. El panel Source Control

El panel Source Control (icono de rama en la barra lateral izquierda, o atajo Ctrl+Shift+G) es tu centro de mando para Git. Desde aquí puedes ver qué archivos han cambiado, añadirlos al área de preparación (stage) y crear commits, todo de forma visual.

Ver los archivos modificados

Cuando editas un archivo, VS Code lo marca automáticamente en el explorador de archivos con una letra:

  • M (Modified) — archivo modificado.
  • U (Untracked) — archivo nuevo que Git aún no conoce.
  • D (Deleted) — archivo eliminado.

En el panel Source Control verás los mismos archivos agrupados en dos secciones: Changes (cambios sin preparar) y Staged Changes (cambios listos para el commit).

Preparar cambios (Stage)

Antes de hacer un commit debes preparar los archivos que quieres incluir. En VS Code tienes dos formas de hacerlo:

  • Haz clic en el icono + que aparece al pasar el ratón por encima de un archivo en la sección Changes para añadirlo individualmente.
  • Haz clic en el + junto al encabezado Changes para preparar todos los archivos a la vez.

Los archivos preparados se moverán a la sección Staged Changes. Si cambias de opinión, haz clic en el icono − para retirarlos del stage.

Crear un commit

Una vez preparados los archivos, escribe un mensaje descriptivo en el campo de texto que dice "Message (Ctrl+Enter to commit)" y pulsa Ctrl+Enter (o haz clic en el botón Commit ✔). El commit quedará registrado en el historial local de tu repositorio.

Consejo: Un buen mensaje de commit responde a la pregunta "¿Qué hace este cambio?", por ejemplo: Añade formulario de contacto.

2. Ramas y merge desde VS Code

Las ramas (branches) te permiten trabajar en una nueva funcionalidad o corrección sin tocar el código principal. VS Code hace que crear y cambiar entre ramas sea tan sencillo como hacer clic en la barra de estado inferior.

Crear una nueva rama

En la esquina inferior izquierda de VS Code verás el nombre de la rama actual (normalmente main o master). Haz clic sobre él para abrir el menú de ramas y selecciona Create new branch…. Escribe el nombre de tu nueva rama (por ejemplo, feature/formulario-contacto) y pulsa Enter.

VS Code creará la rama y cambiará a ella automáticamente. Todos los commits que hagas a partir de ahora irán a esta rama sin afectar a main.

Cambiar entre ramas

Desde el mismo menú de la barra de estado puedes seleccionar cualquier rama existente para cambiar a ella. VS Code actualizará los archivos del proyecto al estado de esa rama de forma instantánea.

Fusionar ramas (Merge)

Cuando tu funcionalidad esté lista y quieras incorporarla a main, sigue estos pasos dentro de VS Code:

  1. Cambia a la rama de destino (main) usando la barra de estado inferior.
  2. Abre la paleta de comandos con Ctrl+Shift+P y escribe Git: Merge Branch….
  3. Selecciona la rama que quieres fusionar (p. ej., feature/formulario-contacto).
  4. Si no hay conflictos, VS Code completará el merge automáticamente y los cambios quedarán integrados en main.

3. Resolución de conflictos visual

Un conflicto de merge ocurre cuando dos ramas han modificado la misma parte de un archivo de forma distinta y Git no puede decidir qué versión conservar. VS Code incluye una herramienta visual que convierte este proceso —habitualmente frustrante— en algo manejable.

Cómo detectar un conflicto

Cuando se produce un conflicto, VS Code marca el archivo con una C roja en el explorador y en el panel Source Control. Al abrirlo, verás el código dividido en bloques con marcadores especiales:

  • <<<<<<< HEAD — inicio de tu versión (rama actual).
  • ======= — separador entre las dos versiones.
  • >>>>>>> feature/… — inicio de la versión entrante (rama que estás fusionando).

Resolver el conflicto con los botones inline

Encima de cada bloque en conflicto aparecen cuatro acciones rápidas. Elige la que mejor se adapte a tu caso:

  • Accept Current Change — conserva únicamente tu versión (HEAD).
  • Accept Incoming Change — conserva únicamente la versión de la otra rama.
  • Accept Both Changes — incluye las dos versiones, una detrás de la otra.
  • Compare Changes — abre una vista de diferencias en dos paneles para decidir con más calma.

También puedes editar el archivo manualmente: simplemente borra los marcadores (<<<, ===, >>>) y deja el código exactamente como quieres que quede.

Finalizar la resolución

Una vez resueltos todos los conflictos del archivo, guárdalo (Ctrl+S). VS Code dejará de marcarlo con la C roja. Repite el proceso con cada archivo en conflicto y, cuando todos estén limpios, ve al panel Source Control y realiza un commit para cerrar el merge:

  1. Prepara los archivos resueltos con +.
  2. Escribe un mensaje como Merge feature/formulario-contacto en main.
  3. Pulsa Ctrl+Enter para confirmar.

¡Enhorabuena! Ahora sabes usar VS Code como tu interfaz principal de Git: puedes preparar y confirmar cambios, trabajar con ramas y superar los conflictos de merge sin necesidad de recordar ningún comando de terminal.
